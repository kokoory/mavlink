1. MOSA 와 미국 Open Architecture 체계
1.1 MOSA 의 본질
미국 DoD 의 Modular Open Systems Approach(MOSA)는 하나의 프로토콜이나 단일 기술 표준이 아니라, 시스템 수
명주기 전체에서 경쟁적·경제적인 획득과 유지, 기술 삽입, 부품 교체, 벤더 종속 완화를 달성하기 위한 통합 비즈니스·기
술 전략이다. 공식 설명은 modular, loosely coupled, highly cohesive structure 와 표준 인터페이스 및 검증 가능한
conformance 를 강조한다.
그림 1-1. MOSA 를 본 프로젝트 관점에서 요약한 구성


 MOSA
   = Modular Design
   + Open / Standardized Key Interfaces
   + Replaceable Components
   + Verifiable Conformance
   + Version / Governance
   + Business & Data-Rights Strategy



따라서 MAVLink, DDS 또는 ROS 2 를 쓴다는 사실만으로 MOSA 가 되는 것은 아니다. 이들은 MOSA 아키텍처를 구현
하기 위한 후보 기술일 뿐이며, 시스템의 모듈 경계와 계약, 교체성, 적합성 시험 및 진화 관리가 함께 설계되어야 한다.

1.3 UCS Architecture Library 에서 가져올 핵심
SAE AS6512B 는 UCS Architecture Revision B 의 Architecture Description 이며 AS6513B 와 AS6518B 를 핵심
연계 문서로 명시한다. AS6518B Architecture Model 은 다른 UCS model/product 의 authoritative source 로 설
명되고, AS6513B 는 UCS product 의 conformance requirement 를 정하는 authoritative specification 이다.
AS6522B 는 architecture model 및 사용자 extension 의 technical governance 를 다룬다.
그림 1-2. UCS 에서 본 프로젝트가 참고하는 구조


 SAE UCS Architecture

 AS6512B   Architecture Description

         |
         +-- AS6518B Architecture Model (authoritative model)
         +-- AS6513B Conformance Specification
         +-- AS6522B Technical Governance / extensions

본 프로젝트는 SAE UCS 를 그대로 복제하거나 “UCS conformant”라고 주장하지 않는다. 대신 Architecture Model 중
심의 설계, 서비스/정보 모델 분리, 명시적 인터페이스, conformance test, extension governance 라는 구조적 원리
를 경량화하여 적용한다.



2. K-MOSA 와 본 프로젝트의 위치
2026 년 설립된 K-MOSA 연구센터는 국방 무인체계의 한국형 MOSA 구현을 목표로 모듈 인터페이스 설계, MUM-T 아
키텍처, AI 자율기능 모듈, 시험·인증 방법론, 정책·표준화 등을 연구 영역으로 제시하고 있다. 즉 국내에서도 단순한 하드
웨어 모듈화가 아니라 인터페이스와 시험·인증까지 포함한 체계적 접근이 중요해지고 있다.

2.1 우리가 풀려는 구체적 문제
        기존 GCS 가 특정 autopilot, 특정 protocol, 특정 payload semantics 와 강하게 결합될 경우 비행체 또는 임무장
         비 교체 때 GCS 수정 범위가 커진다.
        MAVLink 메시지를 그대로 UI/비즈니스 로직에 노출하면 MAVLink 가 사실상 GCS 내부 표준이 되어 다른 프로토콜
         (DDS, UCI, ROS 2)의 삽입이 어려워진다.
        모듈이 교체 가능하려면 단순 통신 연결뿐 아니라 capability, semantic data model, version, timing, behavior,
         conformance 가 명시되어야 한다.
        따라서 GCS 자체가 MOSA 의 Control Segment 축으로 설계되어야 하며, 실제 연결된 UAS architecture 를 이해
         하고 검증할 수 있어야 한다.

2.2 프로젝트의 최종 정의
KM-GCS 는 “Protocol-independent, Vehicle-independent, Payload-modular, Architecture-aware, Capability-
aware Ground Control System”을 목표로 한다. 미국 UCS 의 architecture/conformance/governance 사고방식을
참고하면서도 PX4, ArduPilot, MAVLink, ROS 2, DDS, DroneCAN 등 현재의 오픈 UAS 생태계를 활용한다.

4.1 Air Segment
        Autopilot: PX4 또는 ArduPilot. 실시간 자세/위치 제어, estimator, actuator output, 기본 flight safety 담당.
        Mission Computer: ROS 2 기반 perception, AI, path planning, tracking, higher-level autonomy 담당.
        Payload: EO/IR, gimbal, radar, custom mission payload. 제어 채널과 영상 채널을 분리할 수 있다.


                                                                      5
     Datalink: Wi-Fi/HaLow/Ethernet/RF 등을 물리/링크 기술로 보고, 상위 protocol semantics 와 분리한다.

4.2 Control Segment
KM-GCS 는 차량 운용 UI 만 제공하는 애플리케이션이 아니라 Vehicle, Mission, Payload, Parameter, Health,
Capability 및 Interface Architecture 를 통합하는 Control Segment 다. Architecture View 와
Interface/Conformance 도구가 일반 GCS 와의 핵심 차별점이다.

6. Canonical Domain Model
Canonical Domain Model 은 KM-GCS 의 심장이다. 외부 세계의 protocol-specific representation 을 KM-GCS 내

DDS, ROS 2 가 서로 다른 타입으로 표현해도 Core 는 하나의 모델만 본다.

7.1 핵심 경계
       ILink 는 bytes 를 송수신할 뿐 MAVLink frame 을 알지 못한다.
       IProtocolAdapter 는 framing/parse/encode 를 담당하되 PX4 flight mode 의 의미를 결정하지 않는다.
       IAutopilotAdapter 는 PX4/ArduPilot 제품별 semantic 및 command mapping 을 담당하되 UDP/Serial 을 알지
        못한다.
       VehicleContext 는 protocol object 를 보관하지 않고 canonical state 와 service 집합을 소유한다.
       QML ViewModel/Application Facade 는 domain/service API 만 보고 protocol class 에 직접 접근하지 않는다.

10. 스레드 및 동시성 구조
첫 버전부터 모든 기능을 여러 스레드로 쪼개면 복잡성이 급증한다. 따라서 “I/O 와 장시간 작업만 worker 에 두고
domain state 는 단일 owner thread 에서 갱신한다”는 원칙을 적용한다. Qt 의 queued signal/slot 또는 명시적
EventBus queue 를 cross-thread boundary 로 사용한다.

10.1 State ownership 규칙
1.   VehicleStateStore 의 mutable state 는 Core/Domain thread 만 수정한다.
2.   다른 스레드는 immutable snapshot 또는 event copy 를 사용한다.
3.   Network/Protocol thread 는 VehicleContext 포인터를 직접 만지지 않고 event 를 게시한다.
4.   UI 는 state snapshot/ViewModel property 만 읽고 command 는 service queue 로 보낸다.
5.   Command completion 은 future/callback/signal 형태의 비동기 결과로 반환한다.
6.   종료 시 producer(Network/Protocol)를 먼저 중단한 뒤 Core queue 를 drain 하고 recorder 를 flush 한다.

10.2 Backpressure
ATTITUDE 처럼 고주파 이벤트가 UI 보다 훨씬 빠르게 들어올 수 있다. 모든 sample 을 UI queue 에 쌓지 않는다.
StateStore 는 최신값을 유지하고 UI 는 20~30 Hz 등 제한된 refresh 주기로 snapshot 을 읽는다.
Recorder/Analyzer 만 필요에 따라 모든 sample 을 수신한다. Event 종류별로 Latest-Value, Lossless, Bounded-
Queue 정책을 구분한다.

                    이벤트 유형                                    정책                                           예

 State telemetry                          Latest-value/coalescing                    Attitude, position, battery

 Command/ACK                              Lossless, ordered                          Arm ACK, mission ACK

 Fault/Health                             Lossless + persistence                     Failsafe, component fault

 Raw log                                  Bounded high-throughput queue              MAVLink frames

 UI notification                          Rate-limited                               link quality, HUD refresh

14. ROS 2 와 DDS 의 위치
ROS 2 는 MOSA/UCS 자체가 아니며, 본 설계에서는 주로 Mission Computer 의 autonomy/robotics framework 로
위치시킨다. DDS 는 ROS 2 가 사용할 수 있는 middleware 중 하나이자, KM-GCS 가 직접 연결할 수 있는 data-
centric middleware 로 본다. 최신 ROS 2 문서에서는 DDS 계열뿐 아니라 Zenoh 같은 middleware 선택도 지원하므
로 “ROS 2 = DDS”로 고정하지 않는다.

결론: 구현 직전의 Architecture Baseline
KM-GCS 의 첫 구현은 “QGC 같은 기능을 빠르게 복제”하는 것이 목적이 아니다. 첫 목표는
Link→Protocol→Translation→Domain Event→Vehicle State→Service→UI 라는 경계를 실제 코드에서 유지하면
서 PX4 와 ArduPilot 을 연결하는 것이다. 이 경계가 지켜져야 이후 ROS 2/DDS, Payload, Interface Profile,
Conformance 기능을 Core 재설계 없이 확장할 수 있다.
따라서 다음 작업은 이 문서를 기준으로 repository 를 생성하고, kmgcs_domain → kmgcs_link → kmgcs_mavlink
→ kmgcs_core → kmgcs_ui 순으로 최소 target 을 만들며, PX4 SITL HEARTBEAT 와 ATTITUDE 를 수신해 QML 에
표시하는 첫 수직 절단을 구현하는 것이다. 그 다음 동일 Core 에 ArduPilot SITL 을 붙여 “Autopilot replacement
without GCS core modification”의 최초 검증을 수행한다.
